# キーバインドを端末ツールの慣行に揃える

## Context and Problem Statement

端末上で内容を送り読みする道具は既に多く、利用者は本ツールだけを使うわけではない。
pager、editor、他の棋譜ツールを同じ端末で行き来する。

想定する主な使い方は手を順に送ることなので、移動の操作が慣行から外れると、他の道具から持ち込んだ手癖がそのまま誤操作になる。

一方で、悪手だけを辿るという本ツール固有の操作には、対応する慣行が存在しない。
慣行に無い操作をどのキーに置くかを、慣行に従う範囲と併せて決める。

## Decision Drivers

* 他の端末ツールと行き来したときの誤操作を避けたい。
* 固有の操作を、慣行が既に使っているキーを奪わずに足したい。

## Considered Options

* 端末ツールで広く使われている慣行に揃え、固有の操作は慣行の意味と両立するキーに置く。
* 特定の既存ツールの操作体系をそのまま踏襲する。
* 用途に最適な操作体系を独自に定義する。

## Decision Outcome

端末ツールで広く使われている慣行に揃え、固有の操作は慣行の意味と両立するキーに置く。

ADR-0005 により手順は分岐を持たない線形の列なので、1 手単位の前後移動には左右のキーだけを使う。
矢印キーと vim の `h` と `l` の双方を受け付ける。
上下は 1 手単位の移動に割り当てず、固有の操作のために残す。

特定のツールを基準にする案は採らない。
基準にしたツールの操作が変わるたびに追随の判断が生じ、さらに用途の異なるツールの都合まで引き受けることになる。
慣行そのものを基準にすれば、追随先は変化しない。

独自に定義する案も採らない。
本ツールの利用時間は併用する道具より短く、覚え直しの負担が最適化の利点を上回る。

### 固有の操作の置き場所

悪手だけを辿る移動は上下のキー、すなわち vim の `j` と `k` に置く。
手順リスト上を項目単位で移動する操作であり、vim と pager における上下移動の意味と両立する。
移動の単位が 1 行ではなく次の悪手までである点だけが異なる。

自動再生の開始と停止は `Space` に置く。
pager では `Space` が 1 画面送りだが、本ツールは手順の移動に追随して表示が動くため、利用者が画面送りを直接操作する場面が無い。

### 慣行が割れる場合

同じキーに複数の解釈がある場合、その解釈が本ツールで意味を持つならば pager のものを優先する。
本ツールが最も近いのは、既にある内容を順に読み進める道具だからである。
意味を持たない場合は、そのキーを空きとして扱う。

### Confirmation

手順の前後移動が、矢印キーと `h` / `l` の双方で同じ結果になることをテストで確認する。
上下のキーが手順の前後移動として動作しないことを併せて確認する。

ヘルプ表示に並ぶキーが、実装のキーテーブルと過不足なく一致することをテストで確認する。

## Consequences

### Good

* 他の端末ツールから持ち込んだ手癖がそのまま通る。
* 固有の操作が慣行と意味の近い位置に収まり、覚え直しが要らない。
* 追随すべき対象が特定の実装ではないため、外部の変更で判断を迫られない。

### Bad

* 手順リストを 1 行ずつ上下に送ることができない。
  上下は悪手の移動が占めるため、行単位のスクロールを期待した手癖とは衝突する。
  悪手を順に見るのが最も多い使い方だと想定して引き受ける。
* 本ツールにとって最適とは限らない配置を受け入れることになる。
  操作の習得コストのほうが大きいと判断して引き受ける。
* ここで確定するのは移動と固有操作の骨格だけになる。
  残る割り当てと一覧は実装とヘルプが持ち、この ADR には選定の基準を残す。
