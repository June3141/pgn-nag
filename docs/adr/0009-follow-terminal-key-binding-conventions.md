# キーバインドを端末ツールの慣行に揃える

## Context and Problem Statement

端末上で内容を送り読みする道具は既に多く、利用者は本ツールだけを使うわけではない。
pager、editor、他の棋譜ツールを同じ端末で行き来する。

想定する主な使い方は手を順に送ることなので、移動の操作が慣行から外れると、他の道具から持ち込んだ手癖がそのまま誤操作になる。

一方で、悪手だけを辿るという本ツール固有の操作には、対応する慣行が存在しない。
慣行に無い操作をどのキーに置くかを、慣行に従う範囲と併せて決める。

## Decision Drivers

* 他の端末ツールと行き来したときの誤操作を避けたい。
* 固有の操作を、慣行が既に使っているキーを奪わずに足したい。

## Considered Options

* 端末ツールで広く使われている慣行に揃え、固有の操作は慣行が使っていないキーに置く。
* 特定の既存ツールの操作体系をそのまま踏襲する。
* 用途に最適な操作体系を独自に定義する。

## Decision Outcome

端末ツールで広く使われている慣行に揃え、固有の操作は慣行が使っていないキーに置く。

手順は分岐を持たない線形の列なので、前後移動には左右のキーだけを使う。
矢印キーと vim の `h` と `l` の双方を受け付ける。
上下は手順の移動に割り当てず、固有の操作のために空けておく。

特定のツールを基準にする案は採らない。
基準にしたツールの操作が変わるたびに追随の判断が生じ、さらに用途の異なるツールの都合まで引き受けることになる。
慣行そのものを基準にすれば、追随先は変化しない。

独自に定義する案も採らない。
本ツールの利用時間は併用する道具より短く、覚え直しの負担が最適化の利点を上回る。

### 固有の操作の置き場所

悪手だけを辿る移動は上下のキー、すなわち vim の `j` と `k` に置く。
盤面の手順は左右で送るため上下は空いており、かつ手順リスト上を項目単位で飛ぶ操作は vim の上下移動と意味が近い。

自動再生の開始と停止は `Space` に置く。
pager では `Space` が 1 画面送りだが、本ツールに画面送りの概念は無いため衝突しない。

### 慣行が割れる場合

同じキーに複数の解釈がある場合は pager の解釈を優先する。
本ツールが最も近いのは、既にある内容を順に読み進める道具だからである。

### Confirmation

手順の前後移動が、矢印キーと `h` / `l` の双方で同じ結果になることをテストで確認する。
上下のキーが手順の前後移動として動作しないことを併せて確認する。

実装のキーテーブルとヘルプ表示が同一の定義から生成され、食い違わないことをテストで確認する。

## Consequences

### Good

* 他の端末ツールから持ち込んだ手癖がそのまま通る。
* 固有の操作が慣行の空き地に収まり、既存の意味を上書きしない。
* 追随すべき対象が特定の実装ではないため、外部の変更で判断を迫られない。

### Bad

* 手順の移動に上下のキーを使えない。
  固有の操作を空きキーに置くという方針と引き換えに受け入れる。
* 本ツールにとって最適とは限らない配置を受け入れることになる。
  操作の習得コストのほうが大きいと判断して引き受ける。
* 個々のキーの割り当てはこの ADR では確定しない。
  割り当ての一覧は実装とヘルプが持ち、ここには選定の基準だけを残す。
