# 複雑度を CI でゲートする

## Context and Problem Statement

複雑度の上限は、後から入れるほど導入が難しくなる。
既存のコードが閾値を超えている状態で規則を足すと、まず是正のための改修が必要になり、その改修が終わるまで規則が有効にならない。
結果として規則が入らないまま放置される。

実装が 1 行も無い現時点であれば、是正の対象が存在しないため、閾値をそのまま有効にできる。

一方で、この段階では適切な閾値が分からない。
解析結果を扱う処理がどれだけ分岐を持つかは、書いてみるまで確定しない。

## Decision Drivers

* 是正の対象が無いうちに規則を有効にしたい。
* 閾値を後から調整できる形にしたい。
* 手元と CI で同じ判定が出るようにしたい。
* 導入のために新しい依存や取得物を増やしたくない。

## Considered Options

* clippy が既に持つ lint を有効にし、閾値を `clippy.toml` で指定する。
* `rust-code-analysis` のような計測ツールを取得し、閾値の判定を自前で書く。
* 複雑度のゲートを設けず、レビューで見る。

## Decision Outcome

clippy が既に持つ lint を有効にし、閾値を `clippy.toml` で指定する。

有効にするのは `cognitive_complexity` と `too_many_lines` で、いずれも既定では無効なため `Cargo.toml` の `[lints.clippy]` で宣言する。
`too_many_arguments` は既定で有効なので、閾値だけを下げる。

閾値は既定より厳しくする。
窮屈さが実際に出てから緩めるほうが、緩い状態から締めるより容易である。

計測ツールを取得する案は採らない。
関数ごとの数値は得られるが、閾値の判定を自前で書くことになり、取得物の検証も必要になる。
clippy で不足が出てから検討すればよい。

レビューで見る案も採らない。
閾値を超えたかどうかは機械的に判定できる性質であり、人が毎回数える必要がない。

ファイル単位の行数は clippy に対応する lint が無いため、CI の 1 step として別に見る。

### Confirmation

閾値を超える関数を書いたとき `cargo clippy` が失敗することを確認する。
同じ判定が手元でも出ることを、`Cargo.toml` に宣言を置くことで担保する。

## Consequences

### Good

* 実装の開始時点から閾値が有効になり、是正のための改修が発生しない。
* 手元の `cargo clippy` と CI が同じ判定を出す。
* 閾値の変更が `clippy.toml` の 1 行で済む。

### Bad

* `cognitive_complexity` は clippy の nursery にあり、判定の仕様が変わりうる。
  変わった時点で閾値を調整するか、lint 自体を外す判断をする。
* 閾値を超えた関数が、分割すべきでない場合にも分割を強いられる。
  個別に `#[allow]` を置いて理由を書くことで対処する。
* ファイル単位の行数だけ判定が CI にしか無く、手元では出ない。
  clippy に対応する lint が無いため受け入れる。
