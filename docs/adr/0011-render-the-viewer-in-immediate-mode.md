# viewer を即時モードで描画する

## Context and Problem Statement

viewer は解析済みの棋譜を読み込み、キー入力に応じて現在の手を前後させる。
盤面、手順リスト、評価バー、最善手順は、いずれも現在の手が決まれば一意に定まる。

端末 UI のライブラリには、毎フレームすべてを描き直す方式と、widget が状態を保持しそこへ更新を加える方式がある。
どちらを選ぶかで、モデルと画面の関係が変わる。

## Decision Drivers

* 画面の内容を、現在の手からの純粋な関数として保ちたい。
* 同じ情報をモデルと widget の 2 箇所で持ちたくない。
* 手を 1 つ動かしたときに、更新すべき箇所を数え上げずに済ませたい。

## Considered Options

* 即時モードのライブラリを使い、現在の手から毎フレーム描き直す。
* 保持モードのライブラリを使い、widget の状態を更新する。
* 端末制御のライブラリだけを使い、描画を自前で書く。

## Decision Outcome

即時モードのライブラリを使い、現在の手から毎フレーム描き直す。
実装には ratatui を用いる。

ADR-0001 により viewer は engine を持たないため、ファイルを読み終えた時点で全ての手が確定する。
画面は現在位置を表す添字 1 つの関数になり、途中で値が増える経路が無い。

描画を「現在の手を受け取って画面を返す関数」として書けるため、表示とモデルが食い違う状態が構造的に生じない。
手を 1 つ進めるという操作が、モデルの添字を 1 つ動かすことに閉じる。

保持モードは採らない。
widget が状態を持つと、手を進めるたびに盤面・手順リスト・評価バーの各 widget を個別に更新することになり、更新漏れが表示の食い違いとして現れる。
これは ADR-0006 が禁じている、同じ値を 2 箇所に持つ状態の UI 側での同型になる。

端末への書き出しが差分になるかどうかは、この選択の争点ではない。
即時モードの実装も buffer の差分を取って端末へ送る。

描画を自前で書く案も採らない。
盤面の枠と領域の分割は ratatui の `Block` と `Layout` で足りる。

### Confirmation

`Viewer` が持つ field が、対局と現在位置の 2 つだけであることを確認する。
これは目視での確認になる。

同じ手に移動したとき、経路に依らず同じ画面になることをテストで確認する。

## Consequences

### Good

* 表示がモデルの純粋な関数になり、更新漏れによる食い違いが起きない。
* 手の移動が添字の操作に閉じ、悪手だけを辿る移動も同じ経路で実装できる。
* 描画の検証が、状態を作って画面を組み立てるだけで済む。

### Bad

* 変化の無い部分も毎フレーム組み立てる。
  棋譜 1 局の表示は端末 1 画面ぶんであり、問題が出てから対処する。
* ライブラリの更新に追随する必要がある。
  端末制御は自前で書いても保守が発生するため、引き換えに受け入れる。
