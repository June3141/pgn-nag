# 実装言語に Rust を選ぶ

## Context and Problem Statement

解析工程と閲覧工程の実装言語を決める。
閲覧工程は端末 UI を持つため Rust が有力だが、解析工程だけを別言語にする選択肢もある。

Python には棋譜の木構造、注釈の読み書き、engine プロトコル、評価値の視点変換を備えたライブラリがある。
Rust には同等のものが無く、書き出し側は自作になる。

## Decision Drivers

* 評価値の扱いで起こりやすい誤りを、実行前に検出したい。
* 注釈の解釈を 1 箇所に保ちたい。
* 利用者に言語処理系の導入を要求したくない。

## Considered Options

* 両工程を Rust で実装する。
* 解析工程を Python、閲覧工程を Rust で実装する。
* 両工程を Python で実装する。

## Decision Outcome

両工程を Rust で実装する。

試作の過程で、評価値の符号を手番視点のまま扱う誤り、終局局面に評価値が存在しない場合の扱い漏れ、探索途中の境界値の混入という 3 つの誤りが実際に発生した。
いずれも型で表現できる。
符号は視点を引数に取る変換関数を通さないと値を取り出せない形にでき、評価値の不在は `Option` で強制でき、境界の有無は列挙型の分岐で可視化できる。

解析工程だけを Python に残す案は、注釈の解釈が 2 つの言語に分裂する点で採らない。
閲覧工程には注釈の読み取りが必ず要るため、書き出しはその裏返しとして実装できる。
二重管理を避ける利益が、書き出しを自作する手間を上回る。

### Confirmation

評価値を白視点へ変換する処理が 1 箇所に閉じており、他の経路から値を構築できないことをコードレビューで確認する。

## Consequences

### Good

* 評価値にまつわる 3 つの誤りが、実行前に検出される。
* 単一のバイナリで配布でき、利用者に処理系の導入を求めない。
* 注釈の読み取りと書き出しが同じモジュールに収まり、書式の変更が片側だけに漏れない。

### Bad

* 棋譜の書き出しと注釈の解析を自作することになる。
  主手順のみを対象とするため、書き出しは整形処理の範囲に収まる。
* 手を 1 つ進めるだけで複数の失敗経路を扱うことになり、記述量が増える。
  失敗経路が明示される利点と引き換えに受け入れる。
* 悪手の閾値のような、試行錯誤しながら調整する処理の反復が遅くなる。
  試作した Python の実装を残し、移植の検証と閾値の探索に使う。
